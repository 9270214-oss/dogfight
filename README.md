# 4. Ігровий цикл

Основна логіка ігрового циклу реалізована у файлі:

```text
src/loop.js
```

Для запуску кадрів використовується:

```js
requestAnimationFrame(frame);
```

Симуляція працює з фіксованим timestep:

```js
step = 1 / 60;
```

Це означає, що симуляція намагається виконуватися з частотою приблизно **60 кроків на секунду**, незалежно від частоти оновлення монітора.

Основна частина fixed timestep реалізована через accumulator:

```js
while (accumulator >= step) {
  simulate(step);
  accumulator -= step;
  stepsThisSecond++;
}

const alpha = accumulator / step;

render(alpha);
```

`accumulator` зберігає накопичений час, а `step` визначає фіксований часовий крок симуляції.

# 12. M4.1 — Блокування головного потоку

## Мета

Дослідити, як синхронне блокування головного потоку впливає на роботу Event Loop та рендеринг гри.

## Зміна

У функцію кадру було тимчасово додано навмисне блокування приблизно на 100 мс кожного 60-го кадру:

```js
if (framesThisSecond % 60 === 0) {
  const t = performance.now();

  while (performance.now() < t + 100) {}
}
```

Таким чином, приблизно один раз на секунду головний потік JavaScript блокувався приблизно на 100 мс.

## Результат

Під час експерименту було зафіксовано:

* `steps/s` залишався близько **60**;
* `frames/s` змінювався приблизно в діапазоні **55–60 FPS**;
* `frame time` періодично збільшувався.

Візуально могли виникати короткі ривки анімації.

## Пояснення

JavaScript виконує синхронний код у головному потоці.

Поки виконується:

```js
while (performance.now() < t + 100) {}
```

головний потік зайнятий виконанням цього коду.

Інший JavaScript-код у цей момент не може бути виконаний.

Тому наступні операції, пов'язані з ігровим циклом, повинні чекати завершення блокуючої операції.

Це демонструє принцип роботи Event Loop: якщо Call Stack зайнятий довгою синхронною операцією, інші завдання не можуть бути виконані до її завершення.

## Висновок

Навіть блокування приблизно на 100 мс помітно впливає на плавність рендерингу.

Fixed timestep дозволяє підтримувати стабільний крок симуляції, але не може усунути блокування головного потоку.

Тому тривалі синхронні операції не повинні виконуватися під час кадру гри.

Після експерименту блокуючий код було видалено.

# 13. M4.2 — setInterval замість requestAnimationFrame

## Мета

Порівняти `requestAnimationFrame` та `setInterval` для запуску ігрового циклу.

## Зміна

`requestAnimationFrame` було тимчасово замінено на:

```js
setInterval(() => {
  frame(performance.now());
}, 16);
```

Таким чином, кадр намагався запускатися приблизно кожні 16 мс.

## Результат

Під час експерименту значення `frames/s` та `frame time` помітно коливалися.

Було зафіксовано, наприклад:

```text
56 FPS / 45 ms
48 FPS / 3 ms
57 FPS / 5 ms
```

Через деякий час показники могли знову повертатися приблизно до 60 FPS.

Також було перевірено поведінку після переходу на фонову вкладку приблизно на 5 секунд та повернення до гри.

Після повернення значення статистики тимчасово змінювалися.

## Пояснення

`setInterval` запускає функцію через заданий інтервал часу, але не синхронізований безпосередньо з оновленням зображення браузером.

Крім того, браузер може змінювати частоту виконання таймерів, особливо коли вкладка знаходиться у фоні.

`requestAnimationFrame`, навпаки, спеціально призначений для виконання коду перед наступним перерисовуванням сторінки.

## Висновок

`setInterval` можна використовувати для періодичного виконання JavaScript-коду, але для рендерингу браузерної гри `requestAnimationFrame` краще відповідає механізму оновлення зображення.

Після експерименту `requestAnimationFrame` було відновлено.

# 14. M4.3 — Variable timestep

## Мета

Дослідити, як variable timestep впливає на результат симуляції при різному навантаженні на CPU.

## Зміна

Fixed timestep було тимчасово замінено на variable timestep:

```js
simulate(frameTime);
stepsThisSecond++;

const alpha = 0;
```

У такому варіанті `dt` залежить від фактичного часу між кадрами.

## Експеримент без обмеження CPU

Спочатку було виконано приблизно 5 секунд утримання клавіші `ArrowUp` без обмеження CPU.

Корабель змістився від початкової точки на певну відстань.

## Експеримент з CPU ×6

Після цього в DevTools було встановлено обмеження CPU **6×**.

Експеримент із приблизно 5 секундами утримання `ArrowUp` було повторено.

У цьому випадку корабель опинився **набагато далі від початкової точки**, ніж у першому експерименті.

## Пояснення

При variable timestep значення:

```js
dt
```

залежить від тривалості кадру.

Якщо процесор працює під більшим навантаженням, тривалість кадрів може збільшуватися.

Відповідно, змінюється `dt`, який передається у функцію симуляції:

```js
simulate(frameTime);
```

Через це одна й та сама дія користувача може призвести до різного результату симуляції на системах із різною продуктивністю або при різному навантаженні.

## Висновок

Експеримент показав, що variable timestep робить результат симуляції залежним від тривалості кадрів.

При CPU ×6 положення корабля після приблизно 5 секунд руху помітно відрізнялося від результату без обмеження CPU.

Після завершення експерименту було відновлено fixed timestep:

```js
while (accumulator >= step) {
  simulate(step);
  accumulator -= step;
  stepsThisSecond++;
}

const alpha = accumulator / step;
```

Таким чином, симуляція знову використовує фіксований часовий крок.

# 15. Порівняння fixed timestep та variable timestep

| Характеристика              | Fixed timestep   | Variable timestep  |
| --------------------------- | ---------------- | ------------------ |
| Значення `dt`               | Фіксоване        | Залежить від кадру |
| Залежність від FPS          | Менша            | Більша             |
| Передбачуваність симуляції  | Вища             | Нижча              |
| Поведінка при навантаженні  | Стабільніша      | Може змінюватися   |
| Використання в лабораторній | Основний варіант | Експериментальний  |

Fixed timestep був залишений як основний варіант ігрового циклу.

# 16. Event Loop

JavaScript використовує Event Loop для організації виконання коду та обробки асинхронних подій.

Спрощено роботу можна представити так:

```text
JavaScript code
      ↓
  Call Stack
      ↓
  Event Loop
      ↓
Task / Microtask Queues
      ↓
  виконання коду
```

Синхронний код виконується безпосередньо в Call Stack.

Якщо синхронна операція займає багато часу, головний потік блокується.

Саме це було продемонстровано в експерименті M4.1.

# 17. requestAnimationFrame

`requestAnimationFrame` використовується для планування наступного кадру.

У нашому ігровому циклі:

```js
requestAnimationFrame(frame);
```

викликає функцію `frame` перед наступним оновленням зображення.

Усередині `frame` відбуваються:

1. визначення часу кадру;
2. оновлення accumulator;
3. виконання одного або декількох fixed simulation steps;
4. розрахунок `alpha`;
5. рендеринг;
6. оновлення статистики;
7. планування наступного кадру.

---

# 18. Чому використовується fixed timestep

Fixed timestep потрібен для того, щоб логіка симуляції не залежала безпосередньо від частоти кадрів.

Наприклад, симуляція використовує:

```js
1 / 60
```

секунди для кожного кроку.

Навіть якщо рендеринг тимчасово працює повільніше, симуляція намагається виконати необхідну кількість фіксованих кроків.

Це робить поведінку фізики більш передбачуваною.

# Опис лабораторної роботи №2

**Тема:** Об'єкти, Прототипи та `this`: Модель сутностей (The Entity Model)  
**Курс:** JavaScript — Multiplayer Real-Time Browser Game  

**Мета лабораторної роботи** — дослідити об'єктно-орієнтовані можливості JavaScript, роботу з контекстом `this`, прототипне успадкування та паттерн **Composition over Inheritance** (Композиція замість Успадкування). На практиці необхідно створити базову модель ігрових сутностей (`Entity`), реалізувати кастомну систему колізій, модуль самонаведення об'єктів, систему бонусів (Pickups) та візуальні ефекти рендерингу Canvas.

## 1. Цілі роботи

У межах лабораторної роботи виконано наступні завдання:
- розроблено базовий клас сутності `Entity` з векторною математикою;

- розроблено класи ігрових об'єктів: `Ship`, `Asteroid`, `Bullet`, `Pickup`, `Explosion`;
- реалізовано кастомний модуль виявлення та обробки колізій (`collision.js`);

## 5. Система колізій (Collision Detection)

Логіка перевірки зіткнень реалізована у файлі `src/sim/collision.js`.

Взаємодія об'єктів у грі:
1. **Куля — Астероїд:** знищення кулі, розбиття астероїда на менші уламки або його повне знищення, створення спалаху вибуху (`Explosion`).
2. **Корабель — Астероїд:** відштовхування та нанесення шкоди / руйнування.
3. **Корабель — Pickup:** збирання предмета (відновлення здоров'я або активація підсилення) та видалення об'єкта `Pickup` зі світу.

## 6. Паттерн Композиції та Самонаведення (Composition & Homing)

Для створення самонавідних об'єктів використано компонентний підхід у файлі `src/sim/composition.js`.

Клас `HomingBehavior` містить логіку розрахунку кута та вектора тяги в бік цілі (наприклад, гравця):

export class HomingBehavior {
  constructor(targetTag, speed = 1.2, turnRate = 80) {
    this.targetTag = targetTag;
    this.speed = speed;
    this.turnRate = turnRate;
  }

  update(entity, world, dt) {
    // Пошук цілі та коригування вектора швидкості entity
  }
}

**Застосування в грі:**  
У `src/sim/asteroid.js` астероїд має поле `this.homingComponent = null`. Якщо присвоїти йому екземпляр `HomingBehavior`, астероїд стає самонавідним, змінює колір рендерингу на помаранчевий та починає переслідувати корабель гравця.

## 8. Теоретичний аналіз 1: Контекст `this` у JavaScript

### Проблема втрати контексту
При передачі методу класу як callback-функції (наприклад, у `addEventListener` або `setTimeout`), метод викликається без об'єкта ліворуч від крапки. У результаті значення `this` втрачається (стає `undefined` у строгому режимі або вказує на `window`/DOM-елемент).

### Використані рішення:
1. **Стрілочні функції (Arrow Functions):** зберігають лексичний контекст `this` місця свого оголошення:
   fire = (world) => { /* this вказує на екземпляр класу */ }
2. **Огортання виклику у стрілочну функцію в callback:**
   window.addEventListener('click', () => player.fire(world));
3. **Явна прив'язка через `.bind(this)`** у конструкторі.

---

## 9. Теоретичний аналіз 2: Композиція проти Успадкування

### Чому глибоке успадкування ламається:
Якби гра будувалася на глибокому успадкуванні, ієрархія мала б вигляд:  
`Entity` -> `MovingEntity` -> `HomingEntity` -> `HomingAsteroid` / `HomingBullet`.

Це створює дві проблеми:
- **Дублювання коду:** логіка самонаведення потрібна і для кулі, і для астероїда, але вони знаходяться у різних гілках успадкування.
- **Негнучкість:** важко створити нерухому турель, яка стріляє (потрібна стрільба, але не потрібен рух), або нерухомий самонавідний об'єкт.

### Переваги Композиції (Composition over Inheritance):
Замість створення нових класів через `extends`, поведінка додається як незалежний модуль (компонент). Це дозволяє динамічно додавати або видаляти функціонал об'єкта під час виконання гри.

### 1. Мета роботи
Оволодіти практичними навичками побудови сучасних асинхронних браузерних застосувань на мові JavaScript. Навчитися розробляти надійні конвеєри завантаження ресурсів із підтримкою обробки помилок та фолбеків, будувати слабозв'язану подійну архітектуру (Event Bus) на базі нативного класу `EventTarget`, синтезувати звукові ефекти за допомогою Web Audio API з дотриманням браузерних політик автовідтворення (Autoplay Policy), а також інтегрувати HTTP-інтерфейс вибору кімнат для динамічного налаштування параметрів ігрової сесії.

---

### 2. Теоретичні відомості

1. **Асинхронність та конвеєри завантаження (`Promise.all`, `fetch`):**
   - Використання `Promise.all` дозволяє виконувати паралельне завантаження масиву ресурсів (зображень, аудіофайлів, конфігурацій). У разі збою одного з важливих запитів застосовується механізм `withRetry` із `AbortSignal` для обмеження часу очікування, а також локальні заглушки (fallback), які запобігають перериванню виконання всієї програми при помилках 404.

2. **Подійно-орієнтована архітектура (Event-Driven Architecture):**
   - Шаблон "Шина подій" (Event Bus) на основі `EventTarget` забезпечує повну архітектурну розв'язку (decoupling) між модулями симуляції фізики та модулями відображення/аудіо. Фізичні об'єкти (`Ship`, `Asteroid`, `CollisionManager`) не містять прямих посилань на аудіосистему чи UI, а виключно сповіщають про події через `emitGameEvent()`.

3. **Синтез звуку через Web Audio API:**
   - Web Audio API використовує граф аудіовузлів (`AudioContext`, `OscillatorNode`, `GainNode`). Для задоволення вимог безпеки браузерів (`Autoplay Policy`) запуск або відновлення контексту (`audioContext.resume()`) прив'язується до першої дійсної взаємодії користувача з екраном (клік або натискання клавіші).
   - Процедурний синтез дозволяє генерувати динамічні звуки (постріл, вибух астероїда, руйнування корабля, підбір бонусу) без використання зовнішніх аудіофайлів за допомогою налаштування частотної модуляції (`exponentialRampToValueAtTime`) та огинаючих гучності.

4. **HTTP-мережева взаємодія та оверлейний UI:**
   - Для вибору ігрових сесій використовується асинхронний запит `fetch('/api/rooms')` з обробкою винятків та передачею даних у динамічно створений DOM-елемент (Overlay HTML).

   - Після взаємодії постріли (`Space`), вибухи астероїдів та влучання супроводжуються виразними, м'якими звуковими ефектами відповідної частоти.
   - Модулі фізики не містять прямих викликів аудіокоду, взаємодіючи виключно через `eventBus`.
3. **Перевірка HTTP-лобі та складності (M3):**
   - Перехід до гри відбувається лише після вибору кімнати в лобі.
   - Відображається актуальна статистика заповнення кімнат (`2/4`, `1/2`, `0/4`).
   - При виборі "Оріон-Бета" на полі з'являється підвищена кількість астероїдів, а у верхньому куті Canvas відображається назва обраної кімнати.

### 6. Висновки

Під час виконання лабораторної роботи №3 було повністю досягнуто поставленої мети. Створено асинхронну архітектуру завантаження ресурсів із прогрес-баром та обробкою помилок. Завдяки реалізації шини подій на основі `EventTarget` вдалося повністю віддекуплювати ігрову логіку від звукового супроводу та інтерфейсу. Використання Web Audio API дозволило створити якісне процедурне звучання без залежності від зовнішніх бінарних аудіофайлів. Інтеграція HTTP-лобі забезпечила динамічний вибір кімнат та адаптивну зміну параметрів ігрового світу.
