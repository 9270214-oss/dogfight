# 4. Ігровий цикл

Основна логіка ігрового циклу реалізована у файлі:

```text
src/loop.js
```

Для запуску кадрів використовується:

```js
requestAnimationFrame(frame);
```

Симуляція працює з фіксованим timestep:

```js
step = 1 / 60;
```

Це означає, що симуляція намагається виконуватися з частотою приблизно **60 кроків на секунду**, незалежно від частоти оновлення монітора.

Основна частина fixed timestep реалізована через accumulator:

```js
while (accumulator >= step) {
  simulate(step);
  accumulator -= step;
  stepsThisSecond++;
}

const alpha = accumulator / step;

render(alpha);
```

`accumulator` зберігає накопичений час, а `step` визначає фіксований часовий крок симуляції.

# 12. M4.1 — Блокування головного потоку

## Мета

Дослідити, як синхронне блокування головного потоку впливає на роботу Event Loop та рендеринг гри.

## Зміна

У функцію кадру було тимчасово додано навмисне блокування приблизно на 100 мс кожного 60-го кадру:

```js
if (framesThisSecond % 60 === 0) {
  const t = performance.now();

  while (performance.now() < t + 100) {}
}
```

Таким чином, приблизно один раз на секунду головний потік JavaScript блокувався приблизно на 100 мс.

## Результат

Під час експерименту було зафіксовано:

* `steps/s` залишався близько **60**;
* `frames/s` змінювався приблизно в діапазоні **55–60 FPS**;
* `frame time` періодично збільшувався.

Візуально могли виникати короткі ривки анімації.

## Пояснення

JavaScript виконує синхронний код у головному потоці.

Поки виконується:

```js
while (performance.now() < t + 100) {}
```

головний потік зайнятий виконанням цього коду.

Інший JavaScript-код у цей момент не може бути виконаний.

Тому наступні операції, пов'язані з ігровим циклом, повинні чекати завершення блокуючої операції.

Це демонструє принцип роботи Event Loop: якщо Call Stack зайнятий довгою синхронною операцією, інші завдання не можуть бути виконані до її завершення.

## Висновок

Навіть блокування приблизно на 100 мс помітно впливає на плавність рендерингу.

Fixed timestep дозволяє підтримувати стабільний крок симуляції, але не може усунути блокування головного потоку.

Тому тривалі синхронні операції не повинні виконуватися під час кадру гри.

Після експерименту блокуючий код було видалено.

# 13. M4.2 — setInterval замість requestAnimationFrame

## Мета

Порівняти `requestAnimationFrame` та `setInterval` для запуску ігрового циклу.

## Зміна

`requestAnimationFrame` було тимчасово замінено на:

```js
setInterval(() => {
  frame(performance.now());
}, 16);
```

Таким чином, кадр намагався запускатися приблизно кожні 16 мс.

## Результат

Під час експерименту значення `frames/s` та `frame time` помітно коливалися.

Було зафіксовано, наприклад:

```text
56 FPS / 45 ms
48 FPS / 3 ms
57 FPS / 5 ms
```

Через деякий час показники могли знову повертатися приблизно до 60 FPS.

Також було перевірено поведінку після переходу на фонову вкладку приблизно на 5 секунд та повернення до гри.

Після повернення значення статистики тимчасово змінювалися.

## Пояснення

`setInterval` запускає функцію через заданий інтервал часу, але не синхронізований безпосередньо з оновленням зображення браузером.

Крім того, браузер може змінювати частоту виконання таймерів, особливо коли вкладка знаходиться у фоні.

`requestAnimationFrame`, навпаки, спеціально призначений для виконання коду перед наступним перерисовуванням сторінки.

## Висновок

`setInterval` можна використовувати для періодичного виконання JavaScript-коду, але для рендерингу браузерної гри `requestAnimationFrame` краще відповідає механізму оновлення зображення.

Після експерименту `requestAnimationFrame` було відновлено.

# 14. M4.3 — Variable timestep

## Мета

Дослідити, як variable timestep впливає на результат симуляції при різному навантаженні на CPU.

## Зміна

Fixed timestep було тимчасово замінено на variable timestep:

```js
simulate(frameTime);
stepsThisSecond++;

const alpha = 0;
```

У такому варіанті `dt` залежить від фактичного часу між кадрами.

## Експеримент без обмеження CPU

Спочатку було виконано приблизно 5 секунд утримання клавіші `ArrowUp` без обмеження CPU.

Корабель змістився від початкової точки на певну відстань.

## Експеримент з CPU ×6

Після цього в DevTools було встановлено обмеження CPU **6×**.

Експеримент із приблизно 5 секундами утримання `ArrowUp` було повторено.

У цьому випадку корабель опинився **набагато далі від початкової точки**, ніж у першому експерименті.

## Пояснення

При variable timestep значення:

```js
dt
```

залежить від тривалості кадру.

Якщо процесор працює під більшим навантаженням, тривалість кадрів може збільшуватися.

Відповідно, змінюється `dt`, який передається у функцію симуляції:

```js
simulate(frameTime);
```

Через це одна й та сама дія користувача може призвести до різного результату симуляції на системах із різною продуктивністю або при різному навантаженні.

## Висновок

Експеримент показав, що variable timestep робить результат симуляції залежним від тривалості кадрів.

При CPU ×6 положення корабля після приблизно 5 секунд руху помітно відрізнялося від результату без обмеження CPU.

Після завершення експерименту було відновлено fixed timestep:

```js
while (accumulator >= step) {
  simulate(step);
  accumulator -= step;
  stepsThisSecond++;
}

const alpha = accumulator / step;
```

Таким чином, симуляція знову використовує фіксований часовий крок.

# 15. Порівняння fixed timestep та variable timestep

| Характеристика              | Fixed timestep   | Variable timestep  |
| --------------------------- | ---------------- | ------------------ |
| Значення `dt`               | Фіксоване        | Залежить від кадру |
| Залежність від FPS          | Менша            | Більша             |
| Передбачуваність симуляції  | Вища             | Нижча              |
| Поведінка при навантаженні  | Стабільніша      | Може змінюватися   |
| Використання в лабораторній | Основний варіант | Експериментальний  |

Fixed timestep був залишений як основний варіант ігрового циклу.

# 16. Event Loop

JavaScript використовує Event Loop для організації виконання коду та обробки асинхронних подій.

Спрощено роботу можна представити так:

```text
JavaScript code
      ↓
  Call Stack
      ↓
  Event Loop
      ↓
Task / Microtask Queues
      ↓
  виконання коду
```

Синхронний код виконується безпосередньо в Call Stack.

Якщо синхронна операція займає багато часу, головний потік блокується.

Саме це було продемонстровано в експерименті M4.1.

# 17. requestAnimationFrame

`requestAnimationFrame` використовується для планування наступного кадру.

У нашому ігровому циклі:

```js
requestAnimationFrame(frame);
```

викликає функцію `frame` перед наступним оновленням зображення.

Усередині `frame` відбуваються:

1. визначення часу кадру;
2. оновлення accumulator;
3. виконання одного або декількох fixed simulation steps;
4. розрахунок `alpha`;
5. рендеринг;
6. оновлення статистики;
7. планування наступного кадру.

---

# 18. Чому використовується fixed timestep

Fixed timestep потрібен для того, щоб логіка симуляції не залежала безпосередньо від частоти кадрів.

Наприклад, симуляція використовує:

```js
1 / 60
```

секунди для кожного кроку.

Навіть якщо рендеринг тимчасово працює повільніше, симуляція намагається виконати необхідну кількість фіксованих кроків.

Це робить поведінку фізики більш передбачуваною.

# Опис лабораторної роботи №2

**Тема:** Об'єкти, Прототипи та `this`: Модель сутностей (The Entity Model)

## 1. Цілі роботи

У межах лабораторної роботи виконано наступні завдання:
- розроблено базовий клас сутності `Entity` з векторною математикою;

## 5. Система колізій (Collision Detection)

Логіка перевірки зіткнень реалізована у файлі `src/sim/collision.js`.

Взаємодія об'єктів у грі:
1. **Куля — Астероїд:** знищення кулі, розбиття астероїда на менші уламки або його повне знищення, створення спалаху вибуху (`Explosion`).
2. **Корабель — Астероїд:** відштовхування та нанесення шкоди / руйнування.
3. **Корабель — Pickup:** збирання предмета (відновлення здоров'я або активація підсилення) та видалення об'єкта `Pickup` зі світу.

## 6. Паттерн Композиції та Самонаведення (Composition & Homing)

Для створення самонавідних об'єктів використано компонентний підхід у файлі `src/sim/composition.js`.

Клас `HomingBehavior` містить логіку розрахунку кута та вектора тяги в бік цілі (наприклад, гравця):

export class HomingBehavior {
  constructor(targetTag, speed = 1.2, turnRate = 80) {
    this.targetTag = targetTag;
    this.speed = speed;
    this.turnRate = turnRate;
  }

  update(entity, world, dt) {
    // Пошук цілі та коригування вектора швидкості entity
  }
}

**Застосування в грі:**  
У `src/sim/asteroid.js` астероїд має поле `this.homingComponent = null`. Якщо присвоїти йому екземпляр `HomingBehavior`, астероїд стає самонавідним, змінює колір рендерингу на помаранчевий та починає переслідувати корабель гравця.

## 8. Теоретичний аналіз 1: Контекст `this` у JavaScript

### Проблема втрати контексту
При передачі методу класу як callback-функції (наприклад, у `addEventListener` або `setTimeout`), метод викликається без об'єкта ліворуч від крапки. У результаті значення `this` втрачається (стає `undefined` у строгому режимі або вказує на `window`/DOM-елемент).

### Використані рішення:
1. **Стрілочні функції (Arrow Functions):** зберігають лексичний контекст `this` місця свого оголошення:
   fire = (world) => { /* this вказує на екземпляр класу */ }
2. **Огортання виклику у стрілочну функцію в callback:**
   window.addEventListener('click', () => player.fire(world));
3. **Явна прив'язка через `.bind(this)`** у конструкторі.

---

## 9. Теоретичний аналіз 2: Композиція проти Успадкування

### Чому глибоке успадкування ламається:
Якби гра будувалася на глибокому успадкуванні, ієрархія мала б вигляд:  
`Entity` -> `MovingEntity` -> `HomingEntity` -> `HomingAsteroid` / `HomingBullet`.

Це створює дві проблеми:
- **Дублювання коду:** логіка самонаведення потрібна і для кулі, і для астероїда, але вони знаходяться у різних гілках успадкування.
- **Негнучкість:** важко створити нерухому турель, яка стріляє (потрібна стрільба, але не потрібен рух), або нерухомий самонавідний об'єкт.

### Переваги Композиції (Composition over Inheritance):
Замість створення нових класів через `extends`, поведінка додається як незалежний модуль (компонент). Це дозволяє динамічно додавати або видаляти функціонал об'єкта під час виконання гри.

### 1. Мета роботи
Оволодіти практичними навичками побудови сучасних асинхронних браузерних застосувань на мові JavaScript. Навчитися розробляти надійні конвеєри завантаження ресурсів із підтримкою обробки помилок та фолбеків, будувати слабозв'язану подійну архітектуру (Event Bus) на базі нативного класу `EventTarget`, синтезувати звукові ефекти за допомогою Web Audio API з дотриманням браузерних політик автовідтворення (Autoplay Policy), а також інтегрувати HTTP-інтерфейс вибору кімнат для динамічного налаштування параметрів ігрової сесії.

---

### 2. Теоретичні відомості

1. **Асинхронність та конвеєри завантаження (`Promise.all`, `fetch`):**
   - Використання `Promise.all` дозволяє виконувати паралельне завантаження масиву ресурсів (зображень, аудіофайлів, конфігурацій). У разі збою одного з важливих запитів застосовується механізм `withRetry` із `AbortSignal` для обмеження часу очікування, а також локальні заглушки (fallback), які запобігають перериванню виконання всієї програми при помилках 404.

2. **Подійно-орієнтована архітектура (Event-Driven Architecture):**
   - Шаблон "Шина подій" (Event Bus) на основі `EventTarget` забезпечує повну архітектурну розв'язку (decoupling) між модулями симуляції фізики та модулями відображення/аудіо. Фізичні об'єкти (`Ship`, `Asteroid`, `CollisionManager`) не містять прямих посилань на аудіосистему чи UI, а виключно сповіщають про події через `emitGameEvent()`.

3. **Синтез звуку через Web Audio API:**
   - Web Audio API використовує граф аудіовузлів (`AudioContext`, `OscillatorNode`, `GainNode`). Для задоволення вимог безпеки браузерів (`Autoplay Policy`) запуск або відновлення контексту (`audioContext.resume()`) прив'язується до першої дійсної взаємодії користувача з екраном (клік або натискання клавіші).
   - Процедурний синтез дозволяє генерувати динамічні звуки (постріл, вибух астероїда, руйнування корабля, підбір бонусу) без використання зовнішніх аудіофайлів за допомогою налаштування частотної модуляції (`exponentialRampToValueAtTime`) та огинаючих гучності.

4. **HTTP-мережева взаємодія та оверлейний UI:**
   - Для вибору ігрових сесій використовується асинхронний запит `fetch('/api/rooms')` з обробкою винятків та передачею даних у динамічно створений DOM-елемент (Overlay HTML).

3. **Перевірка HTTP-лобі та складності (M3):**
   - Перехід до гри відбувається лише після вибору кімнати в лобі.
   - Відображається актуальна статистика заповнення кімнат (`2/4`, `1/2`, `0/4`).
   - При виборі "Оріон-Бета" на полі з'являється підвищена кількість астероїдів, а у верхньому куті Canvas відображається назва обраної кімнати.

**Тема:** Розробка мультиплеєрної 2D-гри в реальному часі із серверною синхронізацією, життєвим циклом матчу, лобі-кімнатами та візуальними ефектами (VFX).

**Мета:** Набути практичних навичок розробки мережевих браузерних ігор реального часу на основі протоколу WebSockets та Canvas 2D API; побудувати серверно-авторитетну (Server-Authoritative) модель взаємодії, створити систему ізольованих кімнат, зреалізувати підрахунок балів і умови перемоги, а також інтегрувати розширені візуальні ефекти (частинки, ударні хвилі, трясіння камери).

## 1. Архітектура системи та технологічний стек

* **Клієнтський модуль (`client`):** Створений на базі **Vite**. Використовує HTML5 Canvas API для рендерингу ігрової сцени зі швидкістю 60 FPS, обробляє введення з клавіатури, розраховує локальні фізичні колізії та керує системою візуальних частинок і ефектів камери.

## 3. Опис програмної реалізації модулів

### 3.1. Серверний модуль (`server/src/index.js`)
* **Управління кімнатами (`roomStates`):** Зберігає стан кожної кімнати (`room-1`, `room-2`, `room-3`), масиви астероїдів, аптечок та прапор `gameOver`.
* **Автоматичний спавн бонусів:** За допомогою `setInterval` кожні 12 секунд перевіряється кількість аптечок у кожній кімнаті. Якщо їх менше 3, створюється нова у випадкових координатах і транслюється через `SPAWN_PICKUP`.
* **Контроль перемоги (`checkWinCondition`):** При кожному нарахуванні очок за астероїди (+10) або влучання (+25) перевіряється умова `player.score >= 100`. Якщо умову виконано, стан кімнати змінюється на `gameOver = true`, і всім гравцям кімнати надсилається пакет `GAME_OVER`.

### 3.2. Система частинок та VFX (`client/src/render/particles.js`)
Реалізована клас-система `ParticleSystem`, яка керує двома типами візуальних об'єктів:
1. **Точкові частинки (Particles):**
   * *Thruster Trail:* При натисканні клавіші руху під кутом, протилежним до напрямку корабля, спавняться частинки вогню та диму з випадковим часом життя (0.25 с) та кольорами (`#ff6600`, `#ffcc00`, `#ff0033`).
   * *Explosions:* При знищенні об'єктів вилітає радіальний сніп із 25–35 частинок зі швидкістю до 220 пікселів/сек.
   * *Pickup Burst:* 24 бірюзові частинки, що розлітаються по колу при підборі аптечки.
2. **Ударні хвилі (Shockwaves):**
   * При вибухах створюються кільця плазми, радіус яких плавно збільшується (`arc`), а прозорість (`globalAlpha`) зменшується до повного зникнення.

### 3.3. Ефекти камери та універсальний трекінг (`client/src/main.js`)
* **Screen Shake (Трясіння камери):** Реалізовано функцію `triggerScreenShake(intensity, duration)`. У головному циклі рендерингу `gameLoop` перед малюванням сцени виконується зсув контексту Canvas: `ctx.translate(offsetX, offsetY)`, де відхилення розраховуються через генератор випадкових чисел.
* **Універсальний трекер астероїдів (`updateAsteroidVFX`):** Забезпечує спрацьовування ефекту вибуху та струшування камери для **кожного** астероїда, незалежно від того, як він був знищений (лазером, зіткненням із кораблем чи мережевою подією). Трекер порівнює список живих астероїдів на кожному кадрі та запускає VFX для зниклих об'єктів.

## 4. Життєвий цикл матчу (Match Lifecycle)

1. **Фаза підключення (Lobby):** Гравець обирає кімнату в UI-лобі. Клієнт надсилає `JOIN_ROOM` та отримує початковий стан через `INIT_SELF`.
2. **Активна фаза (Gameplay):**
   * Гравці керують кораблями, стріляють та змагаються за астероїди й аптечки.
   * Локальні колізії обробляються негайно, а результати синхронізуються через WS.
   * При вичерпанні астероїдів клієнт генерує запит `REQUEST_NEW_WAVE`, і сервер надсилає нову хвилю `NEW_WAVE`.
3. **Фінальна фаза (Match Completion):**
   * При наборі 100 очок будь-яким гравцем сервер відправляє `GAME_OVER`.
   * Клієнти блокують обробку клавіш керування.
   * Зверху Canvas малюється модальне вікно: переможець бачить зелене привітання **«🏆 ВІТАЄМО! ВИ ПЕРЕМОГЛИ!»**, а інші гравці — червоне повідомлення з іменем переможця та його підсумковим рахунком.
   * Кнопка **«Повернутися у Лобі»** перезавантажує сесію та повертає гравця до вибору кімнати.

## 1. Суть та мета виконаної роботи

У попередніх версіях гри клієнти самостійно обчислювали власні координати та розсилали їх іншим гравцям. Такий підхід є вразливим до шахрайства (клієнт може підмінити свої координати в DevTools) і призводить до розсинхронізації світу через різну частоту кадрів, дрейф чисел із плаваючою комою та втрату пакетів.

У межах **Лабораторної роботи №5** архітектуру гри повністю переведено на індустріальну модель **авторитативного сервера реального часу (30 Гц)**:
1. **Єдине джерело істини на сервері:** клієнти більше не передають свої координати `(x, y)` — вони надсилають лише керуючі команди (`turn`, `thrust`, `fire`) з порядковим номером `seq`. Сервер перевіряє кожну команду, оновлює стан світу за фіксованим кроком `dt = 1/30 с` і розсилає всім учасникам авторитетні знімки (`SNAPSHOT`).
2. **Миттєвий відгук керування (Client-Side Prediction + Server Reconciliation):** щоб гравець не відчував затримки на час проходження пакета до сервера й назад (RTT), клієнт миттєво прогнозує рух свого корабля локально за тією самою детермінованою фізикою, що й сервер. Коли надходить знімок від сервера, клієнт звіряє позицію за номером `lastSeq` і повторно програє непідтверджені команди.
3. **Плавність відображення суперників (Entity Interpolation):** чужі кораблі оновлюються сервером 30 разів на секунду, тоді як екран рендериться з частотою 60–144 Гц. Клієнт буферизує знімки та малює інших гравців із невеликим зсувом у минуле (`80 мс`), інтерполюючи їхні координати між двома сусідніми знімками.
4. **Оптимізація мережевого трафіку (Binary Protocol):** замість громіздкого текстового формату JSON для високочастотних пакетів (`INPUT`, `SNAPSHOT`, `PING/PONG`) розроблено компактний бінарний протокол на базі `ArrayBuffer` та `DataView` (Little-Endian) із квантуванням кутів у `Int16`.

## 2. Архітектура проєкту та розподіл відповідальності

Проєкт організовано як монорепозиторій (`npm workspaces`), поділений на три незалежні пакети:

### Пакет `shared/` — спільне детерміноване ядро
Містить чистий JavaScript-код без залежностей від браузерного DOM/Canvas або модулів Node.js, завдяки чому однаково виконується як на сервері, так і в браузері:
* **`shared/src/sim.js`** — детермінована фізична модель (`PHYSICS`, `applyInput`, `stepWorld`). Описує прискорення, поворот, інерцію та переміщення об'єктів за фіксований крок часу `dt`. Виключає `Math.random()` та `Date.now()`.
* **`shared/src/prng.js`** — генератор псевдовипадкових чисел `PRNG` на основі алгоритму `mulberry32`. Використовує спільне початкове значення (`seed = 1337`), яке сервер передає клієнту під час підключення, що гарантує ідентичну генерацію подій на всіх вузлах.
* **`shared/src/protocol.js`** — бінарний кодек (`encodeWelcome`, `decodeWelcome`, `encodeInput`, `decodeInput`, `encodeSnapshot`, `decodeSnapshot`, `encodePing`, `decodePing`). Відповідає за пакування та розпакування сирих байтів через `DataView` із явним порядком байтів Little-Endian.
* **`shared/src/index.js`** — єдина точка входу, що реекспортує симуляцію, генератор випадкових чисел та протокол для `server/` і `client/`.
* **`shared/test.js`** — набір автоматичних тестів (Node.js): перевіряє кругове кодування/декодування пакетів (`decode(encode(msg))`), детермінізм симуляції на 1000 кроків та проводить бенчмарк швидкодії й розміру пакетів JSON проти Binary.

### Пакет `server/` — авторитативний ігровий сервер
* **`server/src/index.js`** — головний модуль сервера на базі `node:http` та `ws`:
  * **Точний цикл симуляції (30 Гц):** замість стандартного `setInterval`, який накопичує похибку та дрейфує, використано планування через `setTimeout` відносно абсолютного цільового часу (`nextTick += 1000 / 30`). Сервер вимірює тривалість кожного тіку та джиттер і віддає їх через HTTP-ендпоїнт `GET /api/stats`.
  * **Валідація та захист від спаму (Anti-Cheat / Rate Limit):** функція `validateInputPacket` відкидає пошкоджені або шахрайські команди (наприклад, `turn = 1000` або застарілі `seq`), а алгоритм `Token Bucket` (`allowInputToken`) обмежує максимальну частоту вхідних пакетів від одного клієнта.
  * **Інжектор мережевих умов (`netem`):** функції `calcNetDelay` та `sendWithNetem` дозволяють у реальному часі емулювати затримку мережі (`delay`), розкид затримки (`jitter`) та відсоток втрачених пакетів (`loss`) через параметри URL, ендпоїнт `/api/netem` або гарячі клавіші клієнта.
  * **Підтримка двох кодеків:** основний трафік працює у бінарному режимі, але для порівняльного тестування збережено можливість перемикання клієнта на текстовий JSON (`SET_CODEC`).

### Пакет `client/` — клієнт із передбаченням, інтерполяцією та Netgraph
* **`client/src/main.js`** — головний клієнтський контролер, який поєднує мережевий рівень, фізику з `shared/` та рендеринг:
  * **Client-Side Prediction:** кожні `1/30 с` клієнт зчитує клавіші (`W/A/D` або стрілки), формує команду з інкрементованим `seq`, негайно застосовує її до локального стану `predState` через `applyInput`, зберігає команду в чергу `pendingInputs` і відправляє 8-байтовий бінарний пакет на сервер.
  * **Server Reconciliation та згладжування:** при отриманні бінарного знімка `SNAPSHOT` клієнт видаляє з `pendingInputs` усі команди, які сервер уже врахував (`seq <= lastSeq`), встановлює корабель у позицію сервера та повторно застосовує решту команд із черги. Якщо виникла розбіжність, вектор помилки записується у `smoothOffset` і плавно згасає за ~100 мс, усуваючи різкі ривки.
  * **Entity Interpolation:** функція `interpolateRemoteEntities` зберігає історію останніх 30 знімків у `snapshotBuffer` і обчислює позицію та кут повороту чужих кораблів у момент часу `now - interpDelayMs` між двома опорними знімками.
  * **Netgraph Overlay:** поверх ігрового поля в реальному часі виводиться панель мережевої діагностики (RTT через `PING/PONG`, вік останнього знімка, вхідний/вихідний трафік у Б/с, довжина черги `pendingInputs`, величина поправки reconciliation у пікселях, поточна затримка інтерполяції).
* **`client/src/sim/ship.js`** — модель корабля на клієнті з прапорцем `networkControlled`, який вимикає локальне дублювання фізики та передає керування координатами модулю передбачення й узгодження.
* **`client/src/sim/world.js`** — контейнер ігрового світу (`1200×800`), що керує життєвим циклом сутностей, фоновим зоряним полем і відмальовуванням кадрів.

## 3. Специфікація бінарного протоколу (`v1`, Little-Endian)

Усі бінарні повідомлення передаються через WebSocket у вигляді `ArrayBuffer` (`socket.binaryType = 'arraybuffer'`), використовують порядок байтів **Little-Endian** і починаються зі спільного 2-байтового заголовка (`Byte 0 = version`, `Byte 1 = msgType`):

| Повідомлення | Напрямок | Розмір | Побайтова структура полів |
| :--- | :--- | :---: | :--- |
| **`INPUT` (`1`)** | Client → Server | **8 B** | `[0]` `version: Uint8`<br>`[1]` `type: Uint8` (`1`)<br>`[2..5]` `seq: Uint32` — порядковий номер команди<br>`[6]` `turn: Int8` — поворот (`-1`, `0`, `1`)<br>`[7]` `flags: Uint8` — бітова маска (біт `0`: `thrust`, біт `1`: `fire`) |
| **`SNAPSHOT` (`2`)** | Server → Client | **7 + 16×N B** | `[0]` `version: Uint8`<br>`[1]` `type: Uint8` (`2`)<br>`[2..5]` `tick: Uint32` — номер тіку сервера<br>`[6]` `count: Uint8` — кількість кораблів `N`<br>*Далі для кожного корабля (16 байтів):*<br>`[+0..1]` `id: Uint16` — числовий ідентифікатор гравця<br>`[+2..5]` `lastSeq: Uint32` — останній оброблений `seq` гравця<br>`[+6..9]` `x: Float32` — координата X<br>`[+10..13]` `y: Float32` — координата Y<br>`[+14..15]` `angle: Int16` — кут у $\frac{1}{1000}$ радіан (квантування 2 Б замість 4 Б) |
| **`WELCOME` (`3`)** | Server → Client | **8 B** | `[0]` `version: Uint8`<br>`[1]` `type: Uint8` (`3`)<br>`[2..3]` `id: Uint16` — призначений мережевий ID клієнта<br>`[4..7]` `seed: Uint32` — спільний `seed` для ініціалізації `PRNG` |
| **`PING` / `PONG` (`4`/`5`)** | Обидва | **10 B** | `[0]` `version: Uint8`<br>`[1]` `type: Uint8` (`4` або `5`)<br>`[2..9]` `timestamp: Float64` — мітка часу `performance.now()` для обчислення RTT |

## 5. Аналітичний звіт з мережевої інженерії

### 1. Три фундаментальні проблеми мережевих ігор та їх вирішення
* **Затримка мережі (Latency):** у класичній авторитативній моделі клієнт змушений чекати повний RTT (час туди й назад), перш ніж побачить реакцію свого корабля. У роботі цю проблему вирішено за допомогою **Client-Side Prediction**: клієнт миттєво застосовує натискання клавіш до власного корабля через спільну функцію `applyInput`, завдяки чому керування відчувається миттєвим навіть при затримці `100+ мс`.
* **Узгодженість стану (State Consistency):** через мережевий джиттер і паралельну роботу клієнта та сервера їхні стани можуть розходитися. Це вирішується детермінованою симуляцією (`PRNG` зі спільним `seed` та фіксованим кроком `dt = 1/30`) і механізмом **Server Reconciliation**: при отриманні кожного знімка клієнт відкидає підтверджені сервером команди (`seq <= lastSeq`) і переграє непідтверджені команди поверх позиції сервера, згладжуючи залишкову похибку за ~100 мс.
* **Шахрайство клієнтів (Anti-Cheat):** клієнт сприймається як потенційно скомпрометоване середовище. Він передає лише наміри (натиснуті кнопки), а не кінцеві координати. Сервер перевіряє коректність діапазону значень (відкидає спроби надіслати `turn = 1000` або підробити `seq`) і обмежує частоту запитів алгоритмом Token Bucket, унеможливлюючи телепортацію та спідхак.

### 2. Спостереження за Netgraph до та після ввімкнення Prediction
* **Без Prediction (`[P] Prediction: OFF`, затримка Netem `100 ms`):** корабель починає рух або поворот лише після повернення знімка від сервера (~110–130 мс після натискання клавіші). Керування відчувається «ватним», а при джиттері `±30 мс` рух стає нерівномірним.
* **З Prediction (`[P] Prediction: ON`, затримка Netem `100 ms`):** корабель реагує миттєво (`0 мс` локальної затримки). У полі `Черга input` на Netgraph стабільно утримуються 3–4 непідтверджені пакети (що відповідає 100 мс при частоті 30 Гц), а поправка `Reconc` під час вільного польоту становить `0.00 px`, оскільки прогноз клієнта повністю збігається з розрахунками сервера.

### 3. Експеримент із порушенням детермінізму
Для перевірки чутливості узгодження до недетермінованого коду у функцію `applyInput` на клієнті було тимчасово додано випадкове зміщення координат через `Math.random()`. У результаті сервер і клієнт почали отримувати різні результати для одних і тих самих вхідних команд: показник `Поправка (Reconc)` у Netgraph зріс із `0.00 px` до `15–40 px` на кожному знімку, а корабель почав постійно смикатися («rubber-banding») під час корекції. Після видалення `Math.random()` і повернення чистої детермінованої математики розбіжності зникли.

### 4. Компроміс між затримкою інтерполяції та плавністю
Сервер розсилає знімки з інтервалом `33.3 мс` (`30 Гц`). Якщо встановлювати мінімальну затримку інтерполяції (`33 мс`), будь-який мережевий джиттер або втрата одного пакета призводить до зупинки або ривків чужого корабля, оскільки в буфері бракує другого опорного знімка. Завелика затримка (`150–200 мс`) робить рух ідеально плавним, але суперник відображається занадто далеко в минулому. Оптимальним компромісом обрано **`80 мс`** (~2.4 інтервали знімків): цього достатньо, щоб пережити джиттер `±30 мс` і втрату `2%` пакетів без візуальних ривків, зберігаючи високу актуальність позиції ворога.

## Міграція багатокористувацького ігрового монорепозиторію на суворий TypeScript («Dogfight»)

**Мета роботи:** перевести багатокористувацький мережевий космічний шутер у реальному часі на суворий TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`, `verbatimModuleSyntax: true`), забезпечити наскрізну типобезпеку між клієнтом і авторитативним сервером через спільний пакет `shared`, замінити ручну валідацію протоколу на схеми `Zod`, реалізувати типізований бінарний кодек, вичерпну диспетчеризацію повідомлень через `never` та підтвердити детермінізм симуляції тестами й CI.

## 1. Архітектура та рамкове рішення

Проєкт організовано як **npm workspaces** монорепозиторій із трьох ізольованих пакетів зі спільною суворою типізацією:

```text
dogfight/
├── tsconfig.base.json   # Коренева конфігурація: strict, noUncheckedIndexedAccess, verbatimModuleSyntax
├── shared/              # Спільне ядро: детермінована фізика, протокол (Zod), кодеки, PRNG, тест детермінізму
├── server/              # Авторитативний Node.js WebSocket + HTTP сервер (30 Гц)
└── client/              # Клієнтський застосунок (Vite + HTML5 Canvas 2D + Web Audio + Netgraph)
```

### Ключові архітектурні рішення
1. **Єдина конфігурація суворості та CI-перевірка:** кореневий `tsconfig.base.json` активує `"strict": true`, `"noUncheckedIndexedAccess": true` та `"verbatimModuleSyntax": true`, а кожен пакет (`shared`, `server`, `client`) успадковує його у власному `tsconfig.json`. Оскільки збирач `Vite` лише транспілює код без перевірки типів, статичний аналіз виконується кореневою командою `npm run typecheck` (`tsc --noEmit`), яка автоматично запускається в **CI**.
2. **Детерміноване спільне ядро (`shared`):** фізика симуляції (`applyInput`, `stepWorld`), незмінний вектор (`readonly Vector2`), розрізнені види сутностей (`kind: 'ship' | 'asteroid' | 'bullet' | 'pickup'`) та генератор псевдовипадкових чисел `PRNG` (`Seed: 1337`) винесені в `shared` і однаково виконуються на клієнті (для *Client-Side Prediction*) і на сервері (для авторитативного розрахунку).
3. **Захист межі довіри (Trust Boundary):** типи TypeScript стираються під час компіляції, тому всі зовнішні дані перевіряються під час виконання через `Zod` у `shared/src/protocol.ts` (`parseClientMessage` повертає `ParseResult` замість старого ручного валідатора) та в `server/src/index.ts` (`ServerConfigSchema`). У кожному блоці `catch` використовується тип `unknown`, а кількість приведень `as` зведено до мінімуму (`< 5`, лише на межах конструктора брендованих типів і десеріалізації) за повної відсутності `any`.
4. **Єдиний інтерфейс кодеків (`SnapshotCodec`):** сервер і клієнт працюють із абстракцією `SnapshotCodec`, реалізованою у двох варіантах — компактному бінарному `BinarySnapshotCodec` (`ArrayBuffer` / `DataView` із перевіркою версії протоколу `PROTOCOL_VERSION` та діапазону/довжини буфера) і текстовому `JsonSnapshotCodec` із можливістю перемикання на льоту клавішею `B`.
5. **Компенсація затримок і діагностика:** реалізовано авторитативний серверний цикл 30 Гц із захистом *Token Bucket*, *Client-Side Prediction* + *Server Reconciliation* (із циклічною арифметикою `seq` за модулем 256), *Entity Interpolation* суперників та інтерактивний стенд **Netgraph + Netem**.

## 2. Три пояснені типи з проєкту

### 1. Брендовані типи (`EntityId`, `Seq`, `Tick`, `RoomId`)
```ts
export type Brand<T, B extends string> = T & { readonly __brand: B };
export type EntityId = Brand<number, 'EntityId'>;
export type Seq = Brand<number, 'Seq'>;
export type Tick = Brand<number, 'Tick'>;
export type RoomId = Brand<string, 'RoomId'>;
```
* **Навіщо:** на етапі виконання ідентифікатор сутності, номер пакета керування та номер тіку є звичайними числами (`number`). Через структурну типізацію TypeScript без брендування можна випадково передати `lastSeq` у функцію пошуку корабля, яка очікує `EntityId`. Брендовані типи створюють номінальну несумісність під час компіляції, унеможливлюючи переплутування ідентифікаторів та лічильників.

### 2. Дискриміноване об'єднання та вичерпний `never` (`ParseResult<T>` / `ClientMessage`)
```ts
export type ParseResult<T> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly error: string };

export function assertNever(x: never): never {
  throw new Error(`Необроблений варіант повідомлення: ${JSON.stringify(x)}`);
}
```
* **Навіщо:** функція `parseClientMessage` повертає дискриміноване об'єднання за літералом `ok`, а мережеві повідомлення та ігрові сутності розрізняються за полями `type` і `kind`. Виклик `assertNever(msg)` у гілці `default` кожного `switch` гарантує на етапі компіляції, що при додаванні нового типу пакета або сутності жоден обробник не буде пропущений.

### 3. Узагальнена типізована шина подій (`Bus<GameEvents>`)
```ts
export class Bus<E extends Record<string, unknown>> {
  on<K E extends keyof>(event: K, handler: (payload: E[K]) => void): void { /* ... */ }
  emit<K E extends keyof>(event: K, payload: E[K]): void { /* ... */ }
}
```
* **Навіщо:** обмеження `K extends keyof E` дозволяє підписуватися та генерувати виключно події, оголошені в контракті `GameEvents`, а індексований доступ `E[K]` автоматично прив'язує кожну назву події до її точного типу корисного навантаження (`payload`), усуваючи потребу в `any` чи ручних приведеннях типів у підписниках.

## 3. Що знайшов TypeScript під час міграції

1. **Небезпечне індексування масивів та буферів (`noUncheckedIndexedAccess`):** увімкнення `noUncheckedIndexedAccess` виявило, що звернення за індексом до черги непідтверджених команд (`pendingInputs[0]`), буфера інтерполяції знімків (`snapshotBuffer[i]`) та масиву вершин полігону астероїда (`this.offsets[i]`) може повернути `undefined`. Це змусило додати явні перевірки (`pendingInputs[0] !== undefined`, `this.offsets[i] ?? 1`), що запобігло появі `NaN` у розрахунках фізики та падінням у рантаймі.
2. **Неповнота обробки варіантів повідомлень та сутностей (`switch` + `never`):** додавання вичерпної перевірки через `assertNever` підсвітило місця диспетчеризації мережевих пакетів (`SET_CODEC`, `SET_NETEM`, `REQUEST_NEW_WAVE`) та видів ігрових об'єктів, де нові варіанти ще не мали власних гілок обробки.
3. **Нетипізовані зовнішні межі та мутації `readonly`:** заміна неявного `any` на `unknown` у всіх блоках `catch (err: unknown)` і вхідних буферах WebSocket виявила припущення про наявність `.message` без перевірки `err instanceof Error`, а модифікатор `readonly` у `Vector2` заборонив неконтрольовану мутацію координат у спільних функціях фізики.

## 4. Керування та діагностичний стенд (Netgraph)

| Клавіша | Дія |
| :--- | :--- |
| **`W` / `↑`** | Прискорення (тяга двигуна) |
| **`A` / `←` та `D` / `→`** | Поворот корабля ліворуч / праворуч |
| **`Space`** | Стрілянина |
| **`P`** | Увімкнути / вимкнути **Client-Side Prediction** (`ON` / `OFF`) |
| **`B`** | Перемкнути кодек передачі даних (**`BINARY`** / **`JSON`**) |
| **`1` / `2` / `3`** | Пресети емуляції мережі (`1`: `0 ms`, `2`: `100 ms`, `3`: `100±30ms + 2% втрат`) |
| **`[` та `]`** | Зменшити / збільшити затримку інтерполяції (`33–200 ms`) |

### Метрики панелі Netgraph
* **RTT (Ping):** круговий час затримки пакета до сервера і назад (`мс`).
* **Вік знімка:** час, що минув від моменту отримання останнього `SNAPSHOT` (`мс`).
* **Трафік In / Out:** вхідний та вихідний мережевий потік (`B/s`) — наочно демонструє економію трафіку в режимі `BINARY` порівняно з `JSON`.
* **Черга input:** кількість локальних команд у буфері `pendingInputs`, які очікують підтвердження від сервера.
* **Поправка (Reconc):** величина корекції позиції корабля в пікселях під час узгодження з сервером.

### 1. Перевірка типів, тест на детермінізм та збірка
```bash
npm install
npm run typecheck      # Перевірка всіх пакетів (0 помилок, 0 any, < 5 as)
node shared/test.ts    # Тест на детермінізм симуляції (PRNG + stepWorld)
npm run build          # Продакшн-збірка проєкту
```

### 2. Запуск у режимі розробки (у двох терміналах)
1. **Сервер (30 Гц, порт `3000`):** `npm run dev -w server`
2. **Клієнт (Vite, порт `5173`):** `npm run dev -w client`
3. Відкрийте `http://localhost:5173` у двох вкладках браузера, оберіть спільну кімнату в лобі та перевірте синхронізацію гравців, зіткнення, переслідуючий астероїд, підбір аптечок і роботу панелі **Netgraph**.
